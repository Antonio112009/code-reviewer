Code review that checks its own work.

Code Reviewer is an open-source command-line tool. It reviews your branch with the model you already use, writes down exactly how each bug would break, and has a second model re-read the code before anything is posted to your pull request.

$npm install -g @antonio112009/code-reviewer

MIT licensed · Node.js 24+ · you pay only for the model calls

Code Reviewer finds the base branch, detects the stack from your manifests, runs the static analyzers and picks the checklists that fit this change. No model has been called yet.

The reviewer reads the chunk and follows the code with read-only tools. It reports through a strict schema: lines, severity, and the path from input to failure.

A second model, the critic, gets each finding and reads the code itself. It confirms, rejects or downgrades, and may correct an overstated title.

majorconcurrencyrefunds.ts:6–11

Concurrent refunds can exceed the order total

confirmed · 0.80 → 0.90 Nothing serialises the check on line 6 and the save on line 11, and payments.refund is an external call that cannot be rolled back.

minorbugrefunds.ts:4

A negative amount is not rejected

rejected RefundSchema in src/routes/refunds.ts:5 requires a positive amount before refund() is called.

What survives goes to the terminal, to Markdown, JSON, HTML or SARIF reports, and with --post to the pull request as an inline comment.

code-reviewercommented on line 6

MAJOR · concurrency · Concurrent refunds can exceed the order total

Two refund requests for the same order can both read refunded = 0 and both pass the check, so the customer is refunded up to twice the order total.

Failure path: two POST /refunds for one order → both load the order → both pass line 6 → payments.refund runs twice

Suggestion: reserve the amount in one conditional UPDATE … WHERE refunded + $1 <= total before calling the payment provider.

confidence 0.90 · critic: confirmed

Benchmarks

We measured it the hard way.

Most review tools publish their own numbers. We took the public leaderboard’s own test, 50 pull requests from Sentry, Grafana, Cal.com, Discourse and Keycloak with 158 verified bugs, scored the top tools and ours with one and the same judge, and then audited by hand what the judge called wrong.

60.5

Level with the best

F1 on Martian’s Code Review Bench, under one judge. Qodo Extended, first on the leaderboard, scores 60.5 the same way; Augment, third, 60.6. Nothing else we measured comes closer.

71%

The most precise comments

of what Code Reviewer posts on a pull request matches a verified bug, the highest of any posted report in the comparison. The same model asked for bugs in a single call: 39%.

20 / 20

“False positives” that weren’t

Every posted finding the benchmark counted as wrong turned out, on a blind read of the code, to be a real defect its list had missed. Two were fixed upstream later.

Why we trust these numbers

  • One judge for every row. We re-scored the published tools from the comments they actually posted. Our judge is stricter than the leaderboard’s own, so we never mix the two scales.
  • Two runs, two judges. Every Code Reviewer row is an average of two runs. Judged again by Claude Opus 5.5, no row moved more than 1.3 points and the order held.
  • Audited by hand. Blind auditors read the code behind about 250 findings. After the critic, 95–97% of the main report was real.
  • Reproducible. Every number names its build, command and judge; the raw verdicts are in the repo.

Why Code Reviewer

Not a smarter model. The same models, held to a higher standard of evidence.

Every tool in the comparison above calls the same handful of frontier models. The difference is what you make them prove before a comment reaches a human.

  1. Every finding has to say how it fails.Input, state, code path, consequence. A critical or major finding without a failure path is downgraded before anyone sees it.
  2. A second model has to agree.The critic re-reads the code with its own tools and throws out what it cannot confirm. 95–97% of what survives is a real defect.
  3. It knows your stack by version.853 checklists, loaded per chunk from your manifests. React 19 rules for React 19, not “JavaScript”.
  4. It reads the whole change, twice.Chunks with their related files first, then one pass over the entire diff for what fell between them.
  5. Your model, your account, your machine.Claude, Codex, Gemini, Copilot, Bedrock, any OpenAI-compatible server or a local one. Nothing from the repository is ever executed.
  6. Measured in public.Level with the top of the leaderboard under one judge, and every number’s build, command and raw verdicts are in the repository.

Why it exists

Three ways LLM code review goes wrong, and what we do about each.

01

Comments about code that is fine

A finding has to name the input or state that breaks the code, step by step. Then a second model, the critic, opens the code again and throws out what it cannot confirm. In a blind audit, 95–97% of the findings that reached the main report were real defects.

How the critic decides →

02

The bug sits in a file the reviewer never opened

Before the model starts, Code Reviewer maps where the changed functions are called and where the functions they call are defined. During the review the model can follow those leads with read_file, grep, find_references and git_blame.

What the reviewer sees →

03

Big pull requests get skimmed

The change is split into chunks of related files and every chunk gets its own review. One more call then reads the whole diff at once, looking for what fell between chunks. If any part could not be reviewed, the report says so instead of staying quiet.

Get started

A few questions. Then exactly what to run.

Starting from scratch gets the install, credentials and first review in order. Already installed gets the one command for the case in front of you, with every flag and its cost explained.

    Depth

    Three depths. Which one, and why.

    Reading the code is what costs, not the number of findings. So the cheaper depth saves less than it leaves out, and the deeper one finds what a single pass structurally cannot. Measured on 30 real pull requests, two runs each.

    --essentialFor a CI gate, or when cost matters more than coverage

    Only what can hurt production

    Security, data loss, crashes, leaks, overload, races and expensive queries. Everything reported as critical or major, with a fix.

    Finds2.1% of reviewer comments
    Costs≈ 0.65× full

    About one finding per three pull requests, and every one of them is also in full.

    fulldefaultFor everyday pull requests

    Every real defect

    Edge cases and accessibility too, a sweep over the whole diff for what the chunks missed, and up to five maintainability notes checked to be true. Uncertain findings go to a “worth a look” list that is never posted.

    Finds7.7% of reviewer comments
    Costs$0.40–0.60 per pull request

    Almost four times as many of the comments human reviewers leave as essential, for half as much again. The posted part is 71% precise on real bugs.

    --deepenFor payments, auth, migrations, release branches

    A second, independent pass

    Every chunk is reviewed again by a pass that knows nothing about the first, reasoning harder. What both report is marked, and the critic is told: agreement is evidence.

    Finds15.0% of reviewer comments
    Costs≈ 2.3× full

    One pass misses about a quarter of the real defects two passes find. After a review, the summary suggests it with its estimated cost, and the cache pays the first pass again.

    Safe on untrusted code

    It reads the code. It never runs it.

    • Read-only snapshot. Agents work on an isolated copy of the commit, with read-only tools.
    • Nothing from the repo executes. Linters that load repository configs are opt-in, and programs are never resolved from the reviewed checkout.
    • The repo can’t pick your model. A project config may not choose programs or models, and repository text in prompts is clipped.
    • Local if you need it. With Ollama or any local server, the code never leaves the machine.

    FAQ

    The questions people ask before they install.

    Ask another on GitHub
    How is this different from asking Claude or ChatGPT to review a diff?

    Same model, different standard of evidence. Asked in one call, Claude Sonnet finds more of the known bugs on Martian’s benchmark, but only 39% of its comments point at one. Code Reviewer splits the change into chunks with their related files, loads version-specific checklists, requires a failure path for every serious finding and has a second model verify each one. 71% of what it posts matches a verified bug, and a blind audit of the rest found real defects the benchmark had missed.

    Does it replace human review?

    No. It does the part humans are worst at: reading every line of a large change with the same attention, remembering the version-specific pitfalls of twenty stacks, and following a call three files away. It leaves the design and the judgement calls to the reviewer, and it tries hard not to waste their time with noise.

    How long does a review take, and will it slow down my pull requests?

    One to three minutes for a typical pull request, mostly model time; chunks are reviewed in parallel. In CI it runs alongside your tests. A re-run after a fix pays and waits only for the chunks that changed, because answers for unchanged code come from the cache.

    What happens with false positives?

    Every finding must name the input or state that breaks the code. A second model, the critic, then re-reads the code and rejects what it cannot confirm; what it is unsure about is listed as “worth a look” in the report and never posted. In blind audits 95–97% of the main report was real. When something slips through, the confidence and the critic’s reason are on the comment, so it is quick to dismiss.

    Which models and providers does it work with?

    Claude Code, Codex, GitHub Copilot and Gemini CLIs through their logins; the Anthropic API, AWS Bedrock, OpenAI, OpenRouter, and any OpenAI-compatible server such as Ollama, vLLM, LM Studio or LiteLLM. The review and the verification can use different models and reasoning levels, and if a model is unavailable it offers an alternative.

    Which languages and frameworks does it know?

    Any language the model reads. The 853 skills cover JavaScript and TypeScript with React, Next.js, Vue, Angular, Svelte and Node frameworks; Python with Django, FastAPI and Flask; Go, Java and Kotlin with Spring, C#, Rust, Ruby, PHP, Swift, Dart, Scala, C and C++, shell and SQL; PostgreSQL, MySQL, SQLite, SQL Server, MongoDB, Redis and Elasticsearch; Docker, Kubernetes, Terraform and CI configs. Browse them in the catalog.

    Does my code leave my machine? Do you collect anything?

    Code goes only to the model provider you choose, and never to us: there is no telemetry and no account. The one network call of our own is a daily check for a new version, and CODE_REVIEWER_NO_UPDATE_CHECK=1 turns it off. With Ollama or another local server nothing leaves the machine at all. Agents work on an isolated, read-only snapshot, and nothing from the reviewed repository is executed.

    How much does a review cost?

    You pay only for the model calls. On the 50 benchmark pull requests a full review with Claude Sonnet cost $0.40 to $0.61 each; --essential is about a third cheaper and --deepen about twice the price. --dry-run shows the plan and an estimate before any call, --max-cost caps a run, every run records its cost per stage, and the cache makes re-reviews of the same code free.

    Can it review a whole repository, not just a change?

    Yes: code-reviewer files src/payments reviews the complete files or folders you name, each with its related files as context. It is the way to audit legacy code or a module you inherited; the regular review command is for what changed.

    How do I keep it away from generated files, or point it at what matters?

    review.exclude in .code-reviewer/config.yaml takes globs such as **/*.generated.ts; project.focus names the areas to care about. Rules you already keep in CLAUDE.md, AGENTS.md, .cursorrules or REVIEW.md are read too, and a skill of your own is a Markdown file with a few bullets.

    Where can it post comments?

    GitHub, GitLab, Gitea, Forgejo and Codeberg, Bitbucket Cloud and Data Center, and Azure DevOps: inline comments plus one summary comment that later runs update, with fixed threads resolved. There is a GitHub Action, a GitLab CI template and recipes for the others.

    Is it free?

    The tool is open source under the MIT licence. The only cost is what your model provider charges for the calls, and a local model makes that zero.
