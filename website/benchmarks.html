Benchmarks

How well it finds bugs, measured three ways.

Against bugs that were verified in real pull requests, against what human and LLM reviewers wrote on the same changes, and by auditing our own findings blind. Every number here comes from BENCHMARKS.md, where each one names the build that produced it, the exact command and the judge.

Real bugs

Martian’s Code Review Bench

Martian’s benchmark has 50 pull requests from Sentry, Grafana, Cal.com, Discourse and Keycloak with 158 verified bugs. A judge model reads each review comment and decides whether it describes one of those bugs. Precision is the share of comments that do, recall the share of bugs found, and F1 combines the two.

We judged every row below the same way, with Claude Opus 4.5, including four of the published tools, which we re-scored from the comments they posted on the benchmark. Our judging turned out stricter than the leaderboard’s, so these numbers are lower than the published ones for everybody, and they should be compared only with each other.

Code Reviewer’s rows are release 0.12.0 with its defaults, reviewing through the Anthropic API with Claude Sonnet 5.5, measured on 2026-10-17.

Within 1.5 F1 of the top two

The full report scores 59.1 (58.2 and 60.0 in two runs). Under the same judge Qodo Extended, first on the leaderboard, scores 60.5 and Augment, third, 60.6: less than two runs of one tool can differ by.

The most precise comments

What Code Reviewer posts on a pull request is its main report: 78% of it matches a known bug, the highest precision in this comparison. Less certain findings go to a “worth a look” list in the report.

Checked twice

A second judge, Claude Opus 5.5, moved no row by more than 1.3 F1 points. Judging through the API and through Claude Code agreed within 1.2.

By category

Where it finds bugs, and where it does not.

The same 158 bugs, split by the kind of bug and by how severe the benchmark rates it. Some categories hold only a handful, so one bug moves them by 10 to 25 points; the counts are in the headers.

Strong

Concurrency, 79%: level with Qodo Extended, the best of the published tools. Critical and high bugs, 67% and 69%: as many as Qodo Extended and Augment find.

Weak

Security, 41%, and data integrity, 36%. The same model asked once finds 73% and 79% of them. This is where the next recall work goes.

Closed by --deepen

A second, independent pass lifts security to 64%, logic bugs to 76%, critical bugs to 83% and high ones to 89%, the most of any reviewer here, for lower precision.

Depths

What each depth finds on real bugs.

The same 50 pull requests at each depth of 0.12.0. --essential is a strict filter: almost everything it says is a real bug, but it says little, and misses most serious ones. It suits a cheap CI gate next to a full review, not instead of one. --deepen finds the most, and is worth its price where a missed defect is expensive.

Against the model alone

What the pipeline adds.

The obvious question: is all this better than giving the same model the diff and asking for bugs? We tried exactly that, with Claude Sonnet at the same reasoning effort, in one call, without chunks, tools, skills or a critic.

The single call finds more of the known bugs, 72%. It also writes six comments per pull request, and only 39% of them point at a real one. Code Reviewer’s full report is far more precise and finds fewer bugs: 0.12.0 scores 59.1 against 50.5 (0.7.0 was 8.2 points above, 95% interval +0.7 to +15.4). What the pipeline buys is precision: comments a reviewer can act on.

It is not free. The single call costs about $0.08 per pull request, Code Reviewer about $0.36 on the Anthropic API with Claude Sonnet.

Blind audits

Checking the findings themselves.

Benchmarks only know the bugs on their list. So we also take samples of findings and have auditors label each one real, debatable or wrong, without seeing how it was scored. Two auditors given the same 66 items agreed in 97% of cases.

Before the critic, 61% of the reviewer’s findings were real. After it, 95–97% of the main report was. On Martian, every one of 20 sampled main-report findings that matched no known bug was a real defect: the list is incomplete, so real precision is higher than the benchmark can show, for every tool.

The auditors are models too, so their mistakes may correlate. The protocol and every verdict are in the repository.

Reviewers’ comments

AACR-Bench: what reviewers wrote.

AACR-Bench scores how many of the comments reviewers left on a pull request a tool also makes. 79% of those comments were written by LLM reviewers and 40% are about maintainability, so it rewards volume and breadth more than finding bugs, and absolute numbers are low for everyone. It is still useful for comparing our own settings with each other.

Caveats

What these numbers don’t tell you.

  • Public data. Both benchmarks use well-known public repositories, and their answers are public too. No model or tool on this page can rule out having seen them in training.
  • Incomplete answers. Martian’s list misses real bugs, so correct findings outside it count as wrong. Severity is not scored.
  • Different inputs. The published tools reviewed pull requests with their titles and descriptions, and their comments went through an extraction step. Code Reviewer saw only the diff and the checkout.
  • A different judge path. We call the judge through the Anthropic API, not Martian’s gateway. It scores stricter; our numbers are not adjusted for that.
  • A different review path. 0.12.0 reviewed through the Anthropic API. Through Claude Code the same pipeline finds a little more for a little less precision and costs more (0.8.0: F1 60.5, $0.61 per PR).
  • Noise. Two runs of the same configuration differ by up to 3.7 F1 points on Martian.

Commands to reproduce every run, raw judge verdicts and audit files are in the repository: reproducing the benchmarks.

Benchmarks used: Code Review Bench (Zverianskii, Zhang, Clyne, Garcia, Barez and Upadhyay, 2026, MIT) and AACR-Bench (Zhang et al., 2026). BibTeX.
