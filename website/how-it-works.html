How it works

From a diff to comments you can trust.

A review is eight steps. Only two of them ask a model to find anything. The rest decide what the model sees, check what it says, and make sure no part of the change is skipped without you knowing.

  1. 01

    Pick what to compare

    Code Reviewer works out the base branch the way a pull request would: from the CI event, an open pull or merge request, or your branch rules such as feature/** → develop → main. It fetches the base fresh and reviews what your branch changed since it left it, not what landed on the base in the meantime.

    refs
    $ code-reviewer review --base main --dry-run
Refs  base from flag
      · base main: --base main
      · head HEAD (feature/partial-refunds):
        local branch, including unpushed commits
◆ main … HEAD (feature/partial-refunds)  (1 commit)
  2. 02

    Detect the stack, run the static pass

    Technologies and their versions come from your manifests: package.json, pyproject.toml, go.mod, pom.xml and the rest. Then the fast checks run: secret scanning, about 130 bug-pattern rules, safe external linters and the ast-grep checks that ship with the skills.

    Their hits do not go straight into the report. They become hints on exact lines, and the model has to confirm or reject each one. Leaked secrets and known-vulnerable dependencies are the exception: the critic may lower their severity but cannot drop them.

    stack and analyzers
      stack     Express · PostgreSQL · Node.js · TypeScript
  analyzers Secrets (secretlint) ✓ · Pattern rules ✓
            Added suppressions ✓ · ast-grep ✓
  3. 03

    Group the change into chunks

    Files that belong together, a module with its tests and its imports, go into one chunk sized to fit the model’s context window. Shared files are attached as read-only context instead of being dropped. Every chunk is reviewed; if one fails, for example on a timeout, the report and the pull request summary say which part of the change was not reviewed.

    Each chunk also gets an impact map: where unchanged code uses what changed, and where the functions the new code calls are defined, as file:line. With --expand refs or deep, excerpts of that code are included too.

    --dry-run
    Chunks (1, budget 40,000 tokens each)
  c001  368 tok  timeout 2m 12s  0 hints
        files   src/payments/refunds.ts
        skills  practice/general-bugs (always-on)
                security/core (always-on)
                javascript/core/async-promises
                  (content:/\bawait\b/)
  4. 04

    Load the skills that apply

    A skill is a short checklist for one topic of one technology. A skill is loaded for a chunk only when its technology group matches (the stack, the language, the files, and the version where it matters) and one of its patterns matches a line the change adds. practice/general-bugs and security/core are always on.

    Skills share a token budget per chunk, 6,000 at full depth and 3,500 at essential. The best-scoring ones go in whole; the rest are named by their one-line description, so the model knows they exist.

  5. 05

    Review each chunk, then the whole diff

    The reviewer gets the chunk, its hints and skills, and read-only tools on an isolated snapshot of the commit. It reports through one tool call, submit_findings, with a fixed schema. Critical and major findings must include the path from input to failure.

    At full depth one more call, the sweep, reads the entire diff at once without tools and lists what it finds. On Martian’s benchmark it found bugs the chunk reviews never reported, raising recall by 7.6 to 9.5 points in each of three paired runs. Findings it shares with a chunk review are dropped as duplicates.

    tools the reviewer can call
    read_file        a file of the snapshot, by line range
grep             a regex over the checkout
find_symbol      where a name is declared
find_references  where it is used
list_dir         a directory listing
git_log          recent history of a path
git_blame        who changed a line, and why
  6. 06

    Validate and de-duplicate

    Every finding must point at a real file and real lines near the change. Findings that don’t are dropped with the reason recorded in the run. Findings about the same defect from different chunks or passes are merged. A critical or major finding that gives no failure path is lowered before the critic sees it.

  7. 07

    Let the critic decide

    A second model call verifies each finding with access to the code. It returns a verdict, its own confidence and a reason that refers to the code. It can lower the severity and correct a title that overstates a real defect, and it checks whether a proposed replacement is safe to offer as a one-click suggestion.

    At full depth, findings the critic is unsure about get a second opinion from another verifier.

    VerdictWhat happens
    confirmedKept. Confidence 0.6 or more goes to the main report and the pull request.
    uncertainRe-checked at full depth. Below 0.6, listed under “worth a look” in the reports only.
    rejectedRemoved. Kept in the run record with the critic’s reason.
  8. 08

    Report and post

    You get a live dashboard in the terminal, then reports in Markdown, JSON, HTML, SARIF and GitLab Code Quality format, with the author of each line from git blame and links to the forge. Every run is saved: runs open latest opens the HTML report.

    With --post the findings go to the pull request as inline comments, plus one summary comment that is updated in place. The next run does not repeat comments already there, and it resolves the threads of findings that were fixed.

    terminal
    ! 1 major

  MAJOR  src/payments/refunds.ts:6
         Concurrent refunds can exceed the order total
         conf 0.90 · critic ✓

Anatomy of a finding

What the reviewer has to write down.

Findings come back through a tool call with a strict schema, never as free text. That is what lets every later step check them.

file, lines
Where the defect is, in the new version of the file. Checked against the diff.
severity
critical, major, minor or info. The critic may lower it.
category
bug, security, concurrency, error-handling, performance, resource-leak, api-misuse, data-loss, or maintainability for notes.
description
Why it is a bug: the concrete inputs or state that lead to wrong behaviour.
failurePath
The steps from input to failure. Required for critical and major.
suggestion
How to fix it. Optionally a replacement for the exact lines, which becomes a one-click suggestion if the critic approves it.
confidence
The probability that a senior engineer would agree it is a real defect.
hint, checklist
The static hint it confirms and the skill item that covers it, if any.
submit_findings
{
  "file": "src/payments/refunds.ts",
  "startLine": 6, "endLine": 11,
  "severity": "major",
  "category": "concurrency",
  "title": "Concurrent refunds can exceed the
            order total",
  "failurePath": "two POST /refunds for one order
    → both load the order → both pass line 6
    → payments.refund runs twice",
  "suggestion": "Reserve the amount with one
    conditional UPDATE before refunding",
  "confidence": 0.8
}

Depth

Essential or full, and when to go deeper.

--essentialfull (default)
Looks forSecurity, data loss, crashes and hangs, leaks and OOM, overload, races, costly performanceEvery real defect, including edge cases, accessibility and best practices with a concrete consequence
SeveritiesCritical and majorAll
Skills per chunkEssential ones, 3,500 tokensAll, 6,000 tokens
CriticAlso drops real but low-impact findings; keeps confidence ≥ 0.7Drops claims that are wrong about the code; keeps confidence ≥ 0.3
Second opinionOffOn for findings the critic was unsure about
Whole-diff sweepOff (--sweep)On (--no-sweep)
Maintainability notesOff (--notes)Up to 5, in their own section and the PR summary

--deepen adds an independent second review pass over every chunk at high reasoning, for about twice the price. In a blind audit one pass missed about a quarter of the real defects a second pass found, and findings both passes reported were real three times in four. After a review, the summary suggests --deepen with its estimated cost.

Cost

You see the price before and after.

  • --dry-run shows the plan and a token estimate without calling a model.
  • --max-cost 2 stops starting model calls once $2 is spent.
  • Answers are cached. Re-reviewing the same code costs nothing; after a fix only the changed chunks are reviewed again.
  • --batch on the Anthropic API sends the sweep as a batch request at half price.
  • Per-stage usage. Every run records the tokens and cost of the reviews, the sweep, the critic and the notes.

On Martian’s pull requests a full review with Claude Sonnet costs about $0.40 to $0.61 each.

.code-reviewer/config.yaml
roles:
  review:   { provider: claude, model: sonnet, reasoning: medium }
  critique: { provider: claude, model: sonnet, reasoning: high }
review:
  depth: full
  minConfidence: 0.3
  maxCost: 2
  exclude: ["**/*.generated.ts"]
