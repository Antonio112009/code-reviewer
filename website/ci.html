Code Reviewer/CI setup

CI setup

Review every pull request, on the platform you already use.

One job per pull request: it reviews the change, comments inline with a summary that later runs update in place, and leaves the reports as artifacts. Pick your platform; the provider and the tokens are the only things that change.

GitHub Actions

The official action installs the release, reviews the pull request head, posts inline comments and a summary, uploads SARIF to code scanning and keeps the reports as an artifact.

  1. Add the workflow. Check out the pull request head with full history; the action does the rest.
  2. Add a secret. ANTHROPIC_API_KEY for the Anthropic API, or npm install -g @anthropic-ai/claude-code plus the key for Claude Code, or aws-actions/configure-aws-credentials with an OIDC role and provider: bedrock. Only the review step receives it.
  3. Open a pull request. Comments appear inline; later runs update the summary in place and resolve fixed threads. Inputs: provider, model, depth, fail-on, post, sarif, args, version.
.github/workflows/code-review.yml
# .github/workflows/code-review.yml
name: Code review
on: pull_request
permissions:
  contents: read          # check out the code
  pull-requests: write    # inline comments and the summary comment
  security-events: write  # SARIF to code scanning
jobs:
  review:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v7
        with:
          ref: ${{ github.event.pull_request.head.sha }}   # the pull request head, not the merge commit
          fetch-depth: 0                                   # history for the merge-base
      - uses: antonio112009/code-reviewer@main             # pin a release tag or commit sha
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        with:
          provider: anthropic
          depth: full
          fail-on: major        # optional: fail the job on major findings or unreviewed code

GitLab CI

A template runs on merge request pipelines, posts inline discussions and a summary, and publishes a Code Quality report that GitLab shows in the merge request widget and diff.

  1. Include the template. It runs only on merge_request_event pipelines with full git depth; merged results pipelines are handled.
  2. Two masked variables. GITLAB_TOKEN: a project or group access token with the api scope and the Reporter role, not protected (merge request pipelines are rarely on protected branches). Plus the provider’s key, for example ANTHROPIC_API_KEY.
  3. Variables you can override. CODE_REVIEWER_PROVIDER, _MODEL, _DEPTH, _FAIL_ON, _ARGS, _VERSION, _EXTRA_PACKAGES (for Claude Code: @anthropic-ai/claude-code). Self-managed instances need nothing else.
.gitlab-ci.yml
# .gitlab-ci.yml
include:
  - remote: https://raw.githubusercontent.com/antonio112009/code-reviewer/main/ci/gitlab/code-reviewer.gitlab-ci.yml

code-reviewer:
  variables:
    CODE_REVIEWER_PROVIDER: anthropic
    CODE_REVIEWER_FAIL_ON: major     # optional

Bitbucket Pipelines

Bitbucket Cloud pull requests: inline comments on the new-side line and a summary comment updated in place. Data Center works the same from Jenkins or Bamboo.

  1. Add the pipeline. A full clone is needed for the merge-base; the base branch comes from BITBUCKET_PR_DESTINATION_BRANCH.
  2. Secured variables. BITBUCKET_TOKEN, an API token with pull request write, with BITBUCKET_EMAIL; or a repository access token alone. Plus the provider’s key.
  3. Data Center. BITBUCKET_DC_TOKEN (an HTTP access token) and --forge bitbucket-dc --api-url https://bitbucket.example.com from any CI.
bitbucket-pipelines.yml
# bitbucket-pipelines.yml
image: node:24
pipelines:
  pull-requests:
    '**':
      - step:
          name: Code review
          clone: { depth: full }
          script:
            - npm install -g @antonio112009/code-reviewer
            - code-reviewer review --plain --yes --format md,json --out reports --provider anthropic
            - code-reviewer runs publish latest

Azure Pipelines

Azure DevOps pull requests: threads on the pull request’s own lines and one summary thread updated in place.

  1. Name the source commit. A pull request build checks out the merge commit, so --head $(System.PullRequest.SourceCommitId) anchors comments on the right lines.
  2. Map the token. System.AccessToken must be passed into the posting step explicitly, and the build service identity needs “Contribute to pull requests”.
  3. Elsewhere. Set AZURE_DEVOPS_TOKEN to a personal access token with Code read & write and Pull Request Threads; Azure DevOps Server takes --api-url.
azure-pipelines.yml
# azure-pipelines.yml
trigger: none
pr: [main]
pool: { vmImage: ubuntu-latest }
steps:
  - checkout: self
    fetchDepth: 0
  - task: NodeTool@0
    inputs: { versionSpec: '24.x' }
  - script: npm install -g @antonio112009/code-reviewer
  - script: code-reviewer review --plain --yes --format md,json --out reports --provider anthropic --head $(System.PullRequest.SourceCommitId)
    env: { ANTHROPIC_API_KEY: $(ANTHROPIC_API_KEY) }
  - script: code-reviewer runs publish latest
    env: { SYSTEM_ACCESSTOKEN: $(System.AccessToken) }

Gitea / Forgejo Actions

Gitea Actions, Forgejo Actions and Codeberg run GitHub-style workflows; only the token and the posting step differ.

  1. Add the workflow. The runner sets the GitHub variables; code-reviewer reads the pull request from them and posts to the instance’s own API.
  2. A token. GITEA_TOKEN or FORGEJO_TOKEN with write access to the repository’s issues and pull requests.
  3. Outside Actions. publish.giteaApiUrl in the global config or --api-url; without either, Codeberg’s API is used.
.gitea/workflows/code-review.yml
# .gitea/workflows/code-review.yml  (Forgejo: .forgejo/workflows/)
on: pull_request
jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: actions/setup-node@v4
        with: { node-version: 24 }
      - run: npm install -g @antonio112009/code-reviewer
      - run: code-reviewer review --head ${{ github.event.pull_request.head.sha }} --plain --yes --format md,json --out reports --provider anthropic
        env: { ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }} }
      - run: code-reviewer runs publish latest
        env: { GITEA_TOKEN: ${{ secrets.GITEA_TOKEN }} }

Providers in CI

Which model credentials to give the job.

Anthropic API

The simplest and the cheapest: one secret, ANTHROPIC_API_KEY, and provider: anthropic. No agent in between, prompt caching, and --batch sends the whole-diff sweep at half price.

AWS Bedrock through OIDC

No stored keys. An IAM role that trusts your CI’s OIDC provider for this repository and allows bedrock:InvokeModel; in GitHub aws-actions/configure-aws-credentials with permissions: id-token: write, in GitLab an id_tokens entry. Then provider: bedrock and an inference profile id.

Claude Code with an API key

Install the CLI in the job (npm install -g @anthropic-ai/claude-code), expose ANTHROPIC_API_KEY, and use provider: claude. The agent runs read-only on an isolated snapshot, whatever the repository contains.

OpenAI-compatible

OPENAI_API_KEY or OPENROUTER_API_KEY with --model; any OpenAI-compatible server through a provider of type openai in the global config.

Tokens and safety

What the posting token can and cannot do.

  • Never logged. Tokens come from GITHUB_TOKEN / GH_TOKEN, GITLAB_TOKEN, GITEA_TOKEN, BITBUCKET_TOKEN, AZURE_DEVOPS_TOKEN and appear in no output.
  • Sent to one host. Only to the forge’s API, to the API URL the CI declares, or to the one in the global config or --api-url. A project config, which comes from the checkout under review, may not set these URLs.
  • No surprises from the remote. The repository’s remote only names the repository, and only when its host matches the chosen API: a GitHub Enterprise remote without a configured API URL is an error, never a post to github.com.
  • https only (plain http for localhost), no redirects to another host, a timeout on every request, 429 and 5xx retried three times honouring Retry-After.
  • Only its own comments. De-duplication and in-place updates count the account’s own comments, so it never edits a human’s.

Posting from anywhere

Review in one place, post from another.

Every run is saved. runs publish posts a saved run to its pull request from any machine with a token, and --dry-run shows what would be posted first.

any shell
$ code-reviewer review --base main --format md,json --out reports
$ code-reviewer runs publish latest --dry-run     # what would be posted
$ GITHUB_TOKEN=… code-reviewer runs publish latest
$ code-reviewer runs publish latest --forge gitlab --repo group/project --pr 42
